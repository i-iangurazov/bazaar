# Внутренний поиск по фото: локальный прототип

Поиск в ассортименте одного магазина Bazaar; без платного API, ключей маркетплейсов,
AI-кредитов и тарифного ограничения. Выдаёт до восьми кандидатов. Пользователь сверяет
фотографию и явно выбирает товар. Не создаёт товар, не меняет остатки и не ищет на 1688.

## Запуск разработчиком

Нужны Node из `.node-version`, отдельные PostgreSQL/Redis и Python 3.13. Веса и среда
не входят в git. Проверено на macOS ARM64; Linux/целевой сервер ещё не проверен.
Не используйте клиентскую БД для приведённого тестового сценария.

```sh
python3.13 -m venv .local/product-photo-search/runtime/venv
.local/product-photo-search/runtime/venv/bin/pip install -r services/product-photo-search/requirements.txt
.local/product-photo-search/runtime/venv/bin/python services/product-photo-search/prepare_model.py --with-vision
```

Установщик скачивает официальный PP-ShiTuV2 (около 17 МБ) и PicoDet mainbody
(около 31 МБ), ограничивает размер, проверяет SHA256 и безопасно распаковывает.
Детектор и распознаватель PP-OCRv6, а также классификатор направления PP-OCRv4
берутся из закреплённого RapidOCR 3.9.2; их SHA256 также проверяются.
При старте служба проверяет файлы моделей повторно.
Интернет при обработке снимка не нужен. Без `--with-vision` доступен прежний визуальный
режим; ручная область работает и без OCR, недоступность чтения текста видна в UI.

В среде приложения **и** worker задайте `PRODUCT_PHOTO_SEARCH_URL=http://127.0.0.1:3150`
и одинаковый случайный `PRODUCT_PHOTO_SEARCH_TOKEN` длиной минимум 32 символа. Передайте
токен и процессу Python. Не используйте `NEXT_PUBLIC_*`, не коммитьте токен.

```sh
.local/product-photo-search/runtime/venv/bin/python services/product-photo-search/server.py \
  --model-dir .local/product-photo-search/runtime/models/general_PPLCNetV2_base_pretrained_v1.0_infer \
  --vision-model-dir .local/product-photo-search/runtime/models/vision
pnpm product-photo:worker
```

Миграция `20261114110000_product_photo_features` нужна только в разрешённой среде.
Worker требует те же переменные подключения БД/Redis/хранилища, что и приложение;
как и другие workers Bazaar, он не читает `.env` автоматически: передайте окружение
через свой менеджер процессов. Нужны доступ к R2-фото и/или тот же `public/uploads`
при локальном хранилище. Не открывайте Python-порт пользователям: loopback по умолчанию,
для отдельного сервера — закрытая сеть, TLS и тот же bearer-токен. Без настройки UI
честно показывает, что поиск не подключён. Worker и службу нужно запускать под
менеджером процессов с перезапуском; публикация в production этим изменением не выполняется.

## Поведение и границы

- Кнопка в «Товарах» и на входе в кассу. Сотрудник без доступа к разделу товаров
  выбирает и просматривает результат в окне кассы; прав управления каталогом не получает,
  продажа не создаётся. В «Товарах» выбор открывает существующую карточку. Камера/загрузка через существующие клиентские кодеки, HEIC fallback,
  серверная проверка растровых байтов, ориентации, размера и удаление EXIF. Запрос до 3 МиБ,
  после канонизации JPEG до 1024 px. Сам снимок запроса не записывается в R2 или БД.
- Первая попытка поиска сверяет фото ассортимента с производными признаками и создаёт
  недостающие задания. Это **ленивая подготовка**, без интеграции в транзакции изменения
  товара. Следующий поиск замечает изменения. Несколько ракурсов объединяются по товару.
  Старый признак никогда не используется вместо ещё не готового нового.
- `ProductPhotoFeature`: версия модели + версия источника, один ряд на источник.
  Галерея использует `ProductImage.updatedAt`, legacy `photoUrl` — `Product.updatedAt`:
  изменения карточки с legacy-фото могут потребовать повторной подготовки.
- Worker: атомарный захват с арендой 60 с, тайм-аут задания 30 с, до трёх попыток,
  восстановление просроченной аренды, повтор по кнопке, чередование организаций.
  Устаревшие фото удаляются пакетами после суток, текущие остаются.
  Чтение URL использует существующую защиту от SSRF, проверку DNS, редиректов и размера.
- Проверки организации и доступа к магазину до обработки и повторно перед выдачей.
  Только активный нескрытый ассортимент; архивные/чужие товары исключены. Нулевой остаток
  допустим. Отдаются актуальные цена и остаток магазина, без закупочной стоимости.
  Составной внешний ключ запрещает запись признака к товару другой организации.
- В каждый запрос Faiss поступают только разрешённые текущие признаки. Индекс создаётся
  заново и уничтожается после запроса; общего каталога/индекса пользователей нет.
  Прототип ограничен 10 000 товаров и 10 000 фотографий на магазин, одинаково для всех
  тарифов. Это примерно 27,3 МБ в запросе между Node и Python на верхней границе;
  для больших каталогов понадобится отдельный версионируемый индекс, не платный API.
- Нормализованные 512-мерные FP32, Faiss IndexFlatIP. Экспериментальный порог 0,68
  из открытого стенда; это не вероятность совпадения SKU. Как в официальном PaddleClas,
  PicoDet предлагает до пяти областей с уверенностью от 0,2; распознаются все эти
  области и полный кадр. Маленький предмет не отбрасывается только из-за доли площади.
  Один пакет до шести векторов ищется в одной разрешённой матрице Faiss; результаты
  объединяются по товару и максимальному сходству. Наиболее похожая область выбирается
  для OCR и показа рамки: уверенность детектора в руке/человеке не определяет выбор.
  Пользователь может исправить область готовым `react-easy-crop` или отключить
  автовыделение. Ручная область используется без подмешивания полного кадра.
- RapidOCR/PP-OCRv6 читает текст выбранной области. Точное уникальное совпадение
  нескольких слов с актуальным названием карточки поднимает её среди кандидатов.
  Если визуальный порог не пройден, отдельный результат **по надписи** допустим только
  при дополнительном независимом совпадении марки/модели и наличии подготовленного фото
  в текущем разрешённом ассортименте. UI явно сообщает, что визуальное сходство такого
  результата не подтверждено. Неуверенный, неоднозначный и несовпавший текст не
  подтверждает товар. Нет словаря вкусов ELFBAR, обучения по запросам или индексации
  снимков пользователя. Качество на ассортименте клиентов не установлено.
- Неполная выдача только с явного согласия, с количеством готовых/ошибочных фото.
  При отсутствии похожих кандидатов UI предлагает другой ракурс или поиск по названию.
- Redis ограничивает минутные всплески: 12 запросов на пользователя / 36 на организацию,
  подготовка 90/180, статус 120/240. Нет платного дневного лимита. При недоступности Redis
  обработка закрывается ошибкой. Один активный расчёт Python, параллельные получают 429.
- Paddle и Faiss разделены процессами из-за конфликта OpenMP на Mac. Никакого
  `KMP_DUPLICATE_LIB_OK`. Протокол по приватному socketpair, без прослушивания сети.
  Потеря/тайм-аут ответа уничтожает старый процесс Faiss перед восстановлением, чтобы
  поздний ответ не попал в следующий запрос. Native crash обнаруживается через health.

В `requirements-macos-arm64.lock.txt` сохранена фактически проверенная среда. Перед
переносом на Linux нужно проверить сборку и системные зависимости OpenCV отдельно;
результаты Mac не являются измерением нагрузки production-сервера. Лицензии и
источники моделей — [THIRD_PARTY.md](THIRD_PARTY.md).

Проверка прежних ELFBAR с неизменённой галереей:
`node scripts/qa/product-photo-search-elfbar.mjs evaluate --vision` (с настройками
изолированного QA-аккаунта, описанными в скрипте). Результаты сохраняются отдельно
в `results-vision.json`, исходный протокол не перезаписывается.

## Проверки в одноразовой среде

`scripts/qa/product-photo-search.mjs` закрепляет PostgreSQL 55991, Redis 55992 и приложение
3158, очищает окружение провайдеров, отключает платежи. Он не подключается к рабочей БД.
Тесты имеют дополнительную проверку имени/пользователя БД перед сбросом.

```sh
node scripts/qa/product-photo-search.mjs up
node scripts/qa/product-photo-search.mjs migrate
node scripts/qa/product-photo-search.mjs test tests/integration/product-photo-search.test.ts tests/unit/product-photo-search-engine.test.ts tests/unit/product-photo-search-ui.test.tsx
```

Для настоящей проверки интерфейса на уже загруженных открытых ALOI-фото и модели стенда:
сначала `node scripts/qa/product-photo-search-browser.mjs --seed-only`, затем
в отдельных терминалах `engine`, `worker`, `build`, затем `serve` того же runner;
`node scripts/qa/product-photo-search-browser.mjs`. Этот сценарий создаёт только свои
локальные QA-записи и использует отдельный ракурс `r30`, галерея `r0/r90`. В интеграционных
тестах транспорт модели подменён, в browser-сценарии модель и Faiss настоящие.
Не запускайте сбрасывающие тесты одновременно с browser-сценарием или worker.
Завершите запущенные процессы, затем `node scripts/qa/product-photo-search.mjs down`.

```sh
.local/product-photo-search/runtime/venv/bin/python -m unittest discover -s services/product-photo-search -p 'test_*.py'
```

## Основа

Кодировщик повторяет параметры [официальной конфигурации PaddleClas, commit 202ac79](https://github.com/PaddlePaddle/PaddleClas/blob/202ac79a99aa368f2c95cb1871bbc11574f685da/deploy/configs/inference_general.yaml),
а поиск использует [Faiss](https://github.com/facebookresearch/faiss/wiki/Getting-started).
Исходный PaddleClas — Apache-2.0; Faiss — MIT. Веса берутся из опубликованного пакета
PP-ShiTuV2. Файлы лицензий пакетов следует сохранять при распространении; конкретные
условия весов и клиентские фото проверить перед рабочим запуском, как записано в
[архитектуре](../../docs/product-photo-workflows-architecture.md).
Сравнение качества: [отчёт стенда](../../docs/product-photo-benchmark-20261114.md).
Повторная проверка автовыделения и дополнительных ракурсов:
[измерения и ограничения](../../docs/product-photo-search-multiview-20261114.md).

Дополнительная проверка работающего локального порта 3160: `node scripts/qa/product-photo-search-engine.mjs`.
Она проверяет авторизацию, отказ повреждённому изображению/матрице, восстановление после
неверного ввода и настоящий поиск отдельного ракурса. Использует только одноразовый
тестовый токен из QA-runner, не берёт адрес или ключ рабочей службы из окружения.
