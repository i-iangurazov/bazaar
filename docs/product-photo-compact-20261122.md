# Поиск по фото на 512 МБ — 22 ноября 2026 года

Компактная служба прошла две локальные проверки. Пик всей службы на Debian 13
ARM64 составил 501 542 912 байт при жёстком лимите 512 000 000 байт и
отключённом swap. Bazaar нашёл товар по последней из 63 499 фотографий в
тестовом магазине. Дополнительных облачных ресурсов не создавали.

| Проверка | Результат |
| --- | --- |
| Лимит памяти, 1 CPU | 501,5 МБ, без превышений и завершений из-за памяти |
| 52 парных запроса к старой и новой моделям | Совпали кандидаты выше порога и их порядок, область товара и распознанный текст |
| 63 499 векторов через HTTP службы | 1,55 с, совпадение в последней записи |

| Создание очереди для тех же фотографий | 34,48 с |
| Три одновременных запроса | Один ответ 200 и два ответа 429, служба осталась доступна |

Запросы включали открытые фотографии предметов и продуктов и отдельную
подборку похожих ELFBAR. При визуальном сравнении в обеих версиях совпали
первое место для 9 из 26 присутствующих товаров и выдача кандидатов на 3 из
26 снимков отсутствующих товаров. Это сравнение качества с прежним поиском.
На 11 запросах по ELFBAR также совпали оценки уверенности 12 строк текста
и решения на порогах 0,85 и 0,90.
Выбор совпадения остаётся за пользователем.

Для проверки масштаба база содержала 63 499 строк с фотографиями и
полноразмерными признаками. Последний эталон подготовил настоящий фоновый
обработчик из локального фото. Остальные признаки были синтетическими и
моделировали уже подготовленный каталог. Полная первичная индексация 63 499
разных файлов требует отдельного замера. Проверены запросы без входа и к
недоступному магазину.

Граница памяти относится к HTTP-службе, выделению, Faiss и чтению надписей.
Приложение Bazaar, PostgreSQL, Redis и фоновый индексатор работали отдельно.
Галерея передаётся порциями по 1 024 записи. Выборка из 63 499 записей
занимает около 130 МБ в передаче между приложением и моделью. Для будущего
выката нужны проверка на целевой архитектуре и замер времени и расхода
трафика на реальных подключениях. Запас памяти в этом прогоне составил 10,46 МБ.

## Как устроен режим

Выделение и PP-ShiTu используют те же веса в FP32 в ONNX Runtime. При чтении
надписей в памяти держится одна модель OCR. При обработке строк по одной
сохраняется размер дополнения исходной группы строк. Faiss выполняет
точное сравнение во всех блоках. Из каждого блока в итог переходят восемь
лучших разных товаров для каждого ракурса, чего достаточно для общего
рейтинга. Порог 0,68 и сравнение снимка с несколькими ракурсами сохранились.

Эксперимент включается переменной `PRODUCT_PHOTO_SEARCH_STREAMING=1` в
окружении Bazaar и подключает протокол `packed-f32-v1`. Предел режима составляет
65 536 фото. Без настройки работает прежний протокол. Миграция не нужна.
В запрос уходят признаки, номера групп и снимок без идентификаторов
магазинов, названий, URL фотографий и цен. Право видеть товар, цены и
остатки проверяет Bazaar.

## Локальный повтор

Используйте веса из `prepare_model.py --with-vision`. Для преобразования
запустите `derive_compact_models.py` с PaddlePaddle 3.3.1 и отдельным Python
с Paddle2ONNX 1.3.1. Флаги `--paddle-model-root`, `--exporter-python` и
`--output` указывают исходную папку, интерпретатор преобразования и папку
результата. Оба файла должны совпасть по SHA256 с `compact_weights.py`.

В Linux ARM64 установите зависимости из
`services/product-photo-search/requirements-compact-linux-aarch64.lock.txt`
с `pip install --require-hashes`. Запустите `compact_server.py` с
`--model-dir` для преобразованных весов, `--vision-model-dir` для
папки с OCR, `--threads 1` и тестовым `PRODUCT_PHOTO_SEARCH_TOKEN`.
Ограничьте память всех дочерних процессов через `MemoryMax=512000000`
и `MemorySwapMax=0`. Проверьте `memory.peak` и `memory.events` в cgroup.
Сценарии `scripts/qa/product-photo-compact-check.py` и
`scripts/qa/product-photo-large-catalog.ts` запускаются только в локальной
тестовой среде.
