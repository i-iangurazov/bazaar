# Отчётность Bazaar · матрица и методика выпуска

Исходный main: `47dea07a3dfee7091901638f500bb292e5324a21`. Рабочее дерево было чистым, main синхронизирован fast-forward. Область — отчётность и подтверждённый дефект исторической стоимости возврата. Правила нулевой стоимости, количества, оплаты и складских ограничений не меняются. Миграции этому выпуску не требуются.

## Аудитория и границы данных

- `/reports` и `/reports/analytics`: ADMIN/MANAGER, доступ к аналитике по тарифу и только разрешённые магазины. STAFF/CASHIER перенаправляются на POS, API независимо проверяет роль.
- `/admin/metrics`: ADMIN своей организации, текущая оценка запасов и связанные продажи. Это не аналитика владельца платформы. MANAGER перенаправляется на панель. Платформенный `platformOwnerRouter` остаётся отдельным: MRR, регистрации и межорганизационные данные здесь не добавляются.
- Отчёты суммируют записанные базовые KGS (`*Kgs`; `PurchaseOrderLine.unitCost` также хранит базовую стоимость). Исторические продажи не пересчитываются по текущему курсу магазина. Магазин с валютой USD входит в регрессионный набор.
- Бизнес-календарь приложения фиксирован: Asia/Bishkek, UTC+6. Индивидуального часового пояса организации нет. Начальная дата включена, начало дня после конечной даты исключено. Поддерживается 1–366 дней. Текущий период обрезается временем запроса; сравнение использует такую же прошедшую длительность предыдущего периода. Будущий период не получает выдуманного сравнения.
- Все новые сводки, серии, группировки и экспорты используют единый набор событий `reporting/sales.ts`. Чтение — READ ONLY / REPEATABLE READ с ограничением длительности и свежей проверкой пользователя, подписки и магазинов. Нет серверного кэша отчётов. Браузер не сохраняет устаревший ответ как результат другого фильтра; есть время обновления, обновление вручную и при возвращении фокуса.

## Определения

Продажа — `CustomerOrder`, COMPLETED, `isHeld=false`, известный `completedAt`. Включаются POS и обычные заказы; канал можно выбрать. Черновики, отмены и отложенные чеки исключены. `createdAt` не заменяет дату завершения. Старые датированные ссылки BAAM без `channel` сохраняют прежний POS-контекст; новые ссылки центра явно используют `channel=all`. Старые API `analytics.*` остаются совместимыми с BAAM: их POS-сводка не подменяется суммой всех заказов. Новые три страницы не используют прежнюю товарную строковую аналитику.

Возврат — завершённый `SaleReturn`, учитываемый по собственному `completedAt`, даже если исходная продажа вне периода. Отмена возврата исключает его. Фактическая сумма возврата не пересчитывается по нынешней цене или предполагаемой скидке. Продажи после возвратов = сумма завершённых продаж после скидок − завершённые возвраты.

Историческая себестоимость — `CustomerOrderLine.lineCostTotalKgs`, либо доказуемое `unitCostKgs × qty`, если суммы нет. Оба NULL означают неизвестную стоимость; записанный ноль известен и разрешён. Отрицательные/противоречивые снимки не считаются достоверной стоимостью. Текущий `ProductCost.avgCostKgs` не используется для прошлых продаж. Стоимость возврата выводится из исходной строки: разность округлённых накопленных долей возвращённого количества. Последовательные частичные возвраты полностью возвращают исходную сумму без накопления копеечных ошибок.

Валовая прибыль = продажи после возвратов − себестоимость проданного за вычетом возвращённого. При любой неизвестной стоимости итоговые себестоимость/прибыль/маржа показываются как неполные; отдельно видна подтверждённая часть. Это не чистая прибыль. Маржа = валовая прибыль / продажи после возвратов; наценка = валовая прибыль / себестоимость. Процент неприменим при неположительном знаменателе. Полнота = число строк с известной стоимостью / число строк событий, отдельно показаны нулевые снимки и проблемные строки.

Итог документа и его общая скидка распределяются по стоимости строк методом разностей округлённых накопленных долей: итог всех строк точно равен документу. Скидка относительно сохранённой базовой цены строки учитывается отдельно от скидки корзины. Несогласованные суммы документа отмечаются; документ без распределяемых строк попадает в явную нераспределённую позицию с неизвестной стоимостью.

## Подтверждённые исправления

1. Аналитика показывала только POS, не имела себестоимости/прибыли; фильтры поиска/категории меняли таблицу, но не сводки.
2. Товарная выручка не распределяла скидку документа: строки расходились с карточками.
3. Продажи за 30 дней в admin metrics использовали createdAt, игнорировали возвраты и часть фильтров, превращали NULL-стоимость в ноль.
4. Редактирование завершённого возврата заменяло неизвестную стоимость исходной продажи текущим ProductCost. Новый регрессионный тест выполнен с прежним блоком: падает на 999 вместо NULL; после исправления проходит. Нулевая стоимость сохранена.
5. Предупреждения admin metrics меняли только таблицу; теперь фильтруют ту же группу во всех итогах.
6. Прежний складской экспорт ограничивался загруженной страницей, а «сумма» списаний была количеством. Новый экспорт CSV/XLSX выгружает полный отфильтрованный результат, колонки с единицами, итоги и контекст. Более 10 000 строк — явный отказ с предложением сузить выборку, не тихое усечение.
7. Исправлены неподходящие суммы смешанного журнала, частичные поступления и корректировки только стоимости. Движения и закупки не выдают сумму заказа за фактически поступившие товары.
8. Фильтры/разрез/сортировка/страница сохраняются в URL. Повторная загрузка, возврат браузером и переход к исходному чеку сохраняют контекст. Смена организации/пользователя/роли сбрасывает аудиторию запроса; устаревший экспорт не скачивается.

## Диагностика существующих данных

Воспроизводимый запуск: `node --import tsx scripts/reporting/diagnose.ts --production-read-only`. Использует существующее подключение Vercel в памяти, READ ONLY / REPEATABLE READ, не пишет в БД и не выводит секреты. Артефакт: `artifacts/reporting/production-audit.json`, содержит агрегаты по ID организаций без клиентских имён. Выборка включает существующие QA-организации.

Снимок 10 сентября 2026: 9 284 завершённых документа / 22 322 строки; 1 702 строки без исторической стоимости, 14 348 с явно записанным нулём. В 124 возвратах / 213 строках у 9 строк неизвестна стоимость оригинала. В этой выборке не найдено противоречивых снимков, отсутствующих completedAt, расхождений заголовков со строками или документов без строк. Для неизвестных строк не найдено SALE-движения со стоимостью: доказуемого восстановления из журнала нет. Текущая цена не является доказательством; backfill не применялся. Неизвестная история остаётся явно неполной, не маскируется нулём.

Производительность read-only годового запроса крупнейшей организации: 17 109 строк событий, 1 536 товарных групп, 366 дней — около 1,29 с. В браузер переданы только 25 строк, агрегаты и дневная серия. Это наблюдение на доступном объёме, не обещание для любого объёма; запросы и экспорт имеют ограничения времени/размера. ORM-запросов по одному на строку нет.

## Проверки и ограничения источников

Изолированный набор `tests/helpers/reportingFixture.ts`: две организации, два магазина, RU/EN/KG, четыре роли, POS и обычные заказы, скидки строки/корзины, частичный возврат, отмена/отложенный документ, ноль/NULL/изменённая текущая стоимость, раздельные платежи, границы периода. Отдельные тесты проверяют точное распределение копеек, последовательные возвраты, транзакционный снимок при конкурентной отмене, отзыв доступа перед экспортом и попытки передать чужие ID/организацию.

Браузерная база отдельная от интеграционных тестов; seed отказывается перезаписывать непустую БД. `pnpm test:reports` создаёт production-сборку и проверяет 72 сочетания трёх страниц, ширин 360/390/768/1440, светлой/тёмной темы и RU/KG/EN. Проверяются реальные графики, прокрутка таблиц без переполнения страницы, все десять операционных видов, чек/смена/поставка, фильтры/перезагрузка, полный экспорт за пределами страницы, роли. Дополнительно — loading, empty, partial, сетевой сбой/retry, поздний ответ прежнего фильтра, отказ экспорта и 200% CSS zoom. Это Chromium desktop с изменяемым viewport, не физический телефон. Снимки до/после и состояния: `artifacts/reporting/{before,after,states}`.

Неприменимо без новых источников: чистая прибыль и полный состав расходов, историческая оборачиваемость/средний склад, полноценный финансовый баланс и обязательства поставщикам, MRR/платформенная активность. `/finance/income` и `/finance/expense` ведут к кассовым движениям; отдельного регистра всех расходов нет. Дробные складские количества пока не реализованы (Int в моделях); денежные доли покрыты. Исторический старый API stockouts восстанавливает пересечения нуля по журналу и требует его полноты; новый интерфейс честно показывает текущий дефицит.

## Выпуск

Локально прошли typecheck, lint, i18n:check, 2 010 unit/integration тестов в 290 файлах и production build. После визуальной правки контраста дополнительно повторены 39 профильных unit-проверок и браузерная матрица. Добавлена отдельная обязательная работа CI `reporting-browser`, включённая в `release-gate`; прежние проверки не отключены. Применяется `docs/custom-domain-release.md`: точный SHA, GitHub CI, Vercel READY, production alias и /api/version до/после smoke.

`node --import tsx scripts/reporting/production-smoke.ts --sha=FULL_SHA` создаёт только выделенную INTERNAL QA организацию с синтетическими документами, без платёжных, фискальных и коммуникационных провайдеров. Проверяет SQL и три страницы на реальном www.bazaar.kg, роли и экспорт. В finally отключает QA-пользователей, отзывает сессии и сохраняет аудит. Итоговые SHA/CI/deployment и результаты публикуются в отчёте выпуска; локальная сборка сама по себе не подтверждает production.
