# White native icon and readiness-driven startup

The icon keeps the existing `public/brand/icon.png` pixels, colours and the established 760×714 composition on a 1024² icon. Only the surrounding background changes to opaque white. `scripts/mobile/store-assets.ts` also flattens the existing generated icon onto white for the store; it does not redraw the logo. Store screenshots still require captures of the actual app.

The OS LaunchScreen uses the same existing 560×525 mark on a 2732² canvas, now white in both appearances. `scripts/mobile/generate-assets.ts` additionally writes those exact logo pixels into `StartupLogo.imageset`. The UIKit cover computes the same aspect-fill logo size, so the static launch and animated cover align in portrait and landscape. It gently pulses logo/dot opacity, uses no downloaded animation or dependency, disables animation under Reduce Motion and stops its timer/animations in the background. Failure text supports dynamic type and scrolling on small or landscape screens. Russian, Kyrgyz and English copy is bundled directly in the existing Swift file, without a new resource/PBX file list.

`BazaarStartupCoordinator` lives in the already-compiled bridge controller. It observes WebKit loading/progress/URL without replacing Capacitor's navigation delegate or changing any bridge permissions. Readiness is evaluated in the main frame only, after checking the compiled trusted origin, and checked again when the result returns. A visible `main`/form and the existing hydrated `data-native-runtime="capacitor"` marker are required for a Next.js page. `NativeRuntime` is already mounted by the root `Providers`, including login, so login does not depend on an authenticated-only component. A complete visible plain document without Next.js scripts can also be revealed. Empty or hidden markup and incomplete login SSR do not dismiss the cover.

There is no minimum iOS animation duration and no 900ms iOS wait. The plugin's duplicate launch overlay is disabled with `launchShowDuration: 0` only in the isolated iOS bundle prepared by `scripts/mobile/ios-build-config.ts`; the shared configuration preserves Android's existing 900ms presentation. The iOS copy also explicitly sets white cover/background colours without changing unrelated plugins or the shared source file. The OS launch image and UIKit coordinator provide the iOS presentation. The cover fades only after actual readiness. If readiness is still missing after 20 seconds of foreground loading, or WebKit reaches its untrusted local error document, an explicit localized connection error and retry action replaces the animation. The message makes no claim that a business operation did or did not commit after a lost response. This is a failure cutoff, not a timer pretending that the page is ready. Background time does not consume that allowance. Retry loads only the originally compiled/validated configured address, preserving the same WebKit cookie store. Invalid build configuration has a clear update message and no alternate-host retry. Staging never falls back to the production host.

The existing main-frame/native-origin bridge guard is unchanged. The exact `DEBUG` + `BAZAAR_NATIVE_STOREKIT_TESTS=1` local test-host bypass remains; StoreKit unit hosts do not start a remote page or this presentation. The readiness check adds no JavaScript message handler or callable native API. Apple purchase recovery is unchanged.

Root coordinates asset generation, native compilation and Simulator/device visual checks. Before compiling this source, run the existing asset pipeline so `StartupLogo.png` exists. The source changes alone are not proof of generated PNG pixels, a compiled handoff, reduced-motion/background behaviour or actual device screenshots. `tests/unit/native-startup-readiness.test.ts` executes the exact bundled readiness expression against login/app/plain/hidden/subframe DOM states; native lifecycle, error/retry and visual behaviour still need the actual compiled UI check.

## Observed verification — 2026-11-11

The iOS asset pipeline and store generator completed. Both 1024² store/native icons are opaque RGB with white edges; both 2732² splash appearances are opaque, white and byte-identical. The `contain` resizes explicitly use transparent padding before composition, preventing an unintended black one-pixel padding line without changing the existing logo.

The non-DEBUG `AppStaging/ReleaseStaging` Simulator build `1.0.0/111115` compiled successfully with one build job. Input checksums stayed unchanged during compilation. Its inspected bundle retained all eleven phone plugins, the privacy manifest, fixed isolated Preview origin, white background and iOS-only zero plugin duration. It contained no detected secret markers or StoreKit test assets. This local ad-hoc Simulator artifact does not establish signing for a phone or TestFlight.

Actual Simulator observation showed the white logo/dots and transition to the real Preview login. A temporary copy changed only the configured path on that same trusted Preview origin to its read-only JSON health document, intentionally preventing a ready app surface. After a Home/background return the cover was still loading; foreground timeout then displayed the localized error, and the actual retry button returned to loading. This is an incomplete-document fault, not a demonstrated physical network outage. The original bundle was restored by exact checksum and its normal login observed again; the owned Simulator was then shut down.

The exact readiness expression passed four DOM cases. Twenty staging configuration tests passed, including preservation of Android's timing and source bytes. Reduce Motion, landscape/dynamic type and a real connection outage remain actual-UI checks to perform, followed by the same checks on a real iPhone. The separate Apple completion work is outside this diagnostic bundle's evidence.
