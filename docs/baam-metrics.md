# BAAM metric contract

BAAM reuses the current **completed POS-sale reporting projection** through an [assistant interface](baam-assistant.md). Version `completed-sales-kgs-v1` is implemented by `getBaamSalesMetrics` in `src/server/services/baamMetrics.ts`. This metric service is deterministic and read-only; the assistant separately uses a model to interpret the question. These contracts do not certify excluded POS/inventory producers or production source completeness.

## Scope and access

The caller supplies the authenticated server actor ID. Public router inputs accept only inclusive business dates and an optional store ID; unknown input keys are rejected. The service rereads active membership, organization, ADMIN/MANAGER role, current subscription/analytics entitlement, and current organization-constrained store grants on every call. ADMIN and organization-owner managers can read their organization's stores. Other managers receive their granted stores only. A requested inaccessible store fails closed; an empty grant set never broadens to all stores. No platform-wide organization override exists.

Authorization and monetary reads share one PostgreSQL `REPEATABLE READ`, `READ ONLY` transaction. No response cache is used. Query identity hashes the metric version, organization, resolved ordered store IDs and exact UTC interval. The response audience identifies the authenticated actor; the client must not show another session's cached response. Revocations take effect on the next request; an already running transaction retains its start snapshot.

## Definitions

| Value | Exact meaning |
| --- | --- |
| Sales before returns | Sum of stored `CustomerOrder.totalKgs` for this organization/store scope, `isPosSale=true`, `isHeld=false`, `status=COMPLETED`, non-null `completedAt` in the period. This is already after recorded discounts. It is not undiscounted gross revenue. |
| Recorded discounts | Sum of those orders' `discountKgs`; informational, never subtracted a second time. |
| Returns | Sum of stored `SaleReturn.totalKgs` with `status=COMPLETED` and its own non-null completion time in the period. A return may relate to a sale outside the period. |
| Net sales | Sales before returns minus completed returns. Negative values are valid. This is not profit or tax revenue. |
| Receipt / return counts | Counts of the qualifying completed records, independently of payment-row count. |
| Average receipt | Sales before returns divided by receipt count, rounded to two decimals. BAAM returns `null` when there are no qualifying receipts. |
| Payment methods | Sum actual `SalePayment.amountKgs` rows grouped by CASH/CARD/TRANSFER/OTHER for the qualifying completed sales. Refunds are a separate breakdown. Both payment and related sale/return organization must match. Split rows sum; missing/overpaid rows are not fabricated or balanced. |
| Reconciliation | Payment sum minus sales, and refund sum minus returns. `paymentsReconcile` is true only when both differences round to zero. An empty scope can reconcile arithmetically without proving completeness. |

All monetary values are recorded KGS, rounded to two decimals after SQL aggregation. BAAM does not apply today's store exchange rate, infer historical FX or add currency balances together. The current report UI may format the same KGS values into the user's store display currency; that presentation conversion is outside BAAM's accounting contract. Current arithmetic uses JavaScript numbers after SQL decimals, as the existing reports do; large values beyond precise floating-point cent arithmetic are not certified.

Dates are valid `YYYY-MM-DD` calendar dates, ordered, at most 366 days. The configured business zone is `Asia/Bishkek` (UTC+06:00); the implementation uses that fixed offset. Date endpoints are inclusive in the business zone and translated to a half-open UTC range `[fromUtc, toUtcExclusive)`. September 1, 2026 starts at August 31 18:00 UTC. Future timezone-rule changes require a metric version and implementation review. Missing days are zero-filled. BAAM has no cashier/register inputs. Existing report cashier filters attribute a sale to its creator and a return to its completer, falling back to creator only if the completer is null; totals and refunds now use the same rule.

## Product and older chart boundaries

`getSoldProductsAnalytics` now unions sale and return activity **before** pagination and category/search filtering, so return-only products are included with zero sold quantity and negative net revenue/quantity. Product category options use both populations. Group identity is product ID plus variant key, and deterministic ordering is recorded sale revenue descending, sold quantity descending, name, product ID, variant key. Product metadata is current, organization-constrained metadata. Average price is sale line revenue divided by sold quantity, zero in the existing table if there were no sales. Separate order-wide adjustments are not allocated into product lines; summing product lines need not equal the order-level overview when the stored projections differ. Stock remaining is an existing supporting read, **not certified and not exposed by BAAM**; monetary tests stub that read and never access stock records.

The sold-products export is explicitly the currently visible filtered **page**, using the same rows and monetary formatter as the table. Its filename includes the page number. It is not a full-range/all-pages export. Its contract preserves return-only rows, negative values, barcode strings, missing metadata and column ordering. Shared CSV/XLSX encoding is unchanged.

Older `analytics.getSalesTrend` / `getTopProducts` charts have a different contract: completed orders across channels, a rolling UTC period, no returns deducted, and existing 180-second cache. Historical line margin uses stored `lineCostTotalKgs`, otherwise stored `unitCostKgs × qty`; known zero cost is valid, any missing historical cost in the scoped population withholds the profit ranking, including missing cost below the top-ten cutoff. Current catalog prices/costs are never substituted. Rankings select the requested metric before LIMIT. These line margins exclude returns and separate order-wide adjustments and must not be described as business net profit. Their versioned cache separates organization, store set, range, bucket and ranking metric; equivalent sorted store sets may share a result. Cache corruption/outage behavior and simultaneous mixed-scope legacy arguments are not certified. BAAM bypasses this cache completely.

## Freshness and unknowns

`queryStartedAt` and `queriedAt` describe this database query, not when upstream business activity was fully ingested. `sourceCompleteness` is always `unknown`; `sourceCompleteThrough` is always null because no trustworthy watermark is available. A completed snapshot cannot prove no missing receipts, late returns, duplicates, offline uploads or upstream data errors. A zero means no qualifying value in that snapshot, not proof of no business activity. The metric response represents empty records, missing averages, payment differences and unknown completeness explicitly. The assistant renders the figures relevant to the question and includes its scope and evidence. It must never turn missing cost, unknown source coverage, absent data or a failed query into a confident financial explanation.

Excluded: profit, inventory/stock recommendations, demand forecasts, tax, expense/cash-flow accounting, all-channel revenue, customer/employee profiling, automated decisions, provider actions, and production-data reconciliation. No dedicated POS/inventory implementation or tests are part of this certification.

## Verification and release bounds

Evidence is in `artifacts/bazaar-continuation/20260905/`. `metrics-before.json` records four failing application assertions before fixes (and one passing combined contract); `metrics-filter-before.json` records the return-only category omission after row pagination was corrected. `metrics-after.json` and `metrics-unit.json` record the final focused runs. The SQL suite uses connection-local TEMP reporting projections on the fixed disposable database, including real Prisma payment relation filters; no operational receipt, return, payment or stock fixture is created. Existing historical-cost SQL tests are also rerun. Unit contracts cover fresh membership/role/grants, entitlement, query identity, unknown completeness/average, payment differences, cache separation/TTL and visible-page export.

These tests certify implemented query semantics against controlled fixtures. They do not certify production source completeness, excluded producer correctness, high-volume performance or financial reconciliation against an external ledger. Runtime model/configuration was **NOT EXPOSED**; no model identity is inferred.

The two old CI consumers in `tests/integration/analytics.test.ts` and the reporting assertion in `tests/integration/store-isolation.test.ts` now use `tests/helpers/recordedSalesProjection.ts`, preserving positive monetary/unit assertions and negative ungranted-store coverage. Their existing mixed suites were **not executed locally** because other setup/tests invoke excluded inventory/POS paths. The helper itself passes a separate focused real-SQL test with allowed-store, denied-store and foreign-organization projections. It inserts only TEMP rows and restores its query spy before the unchanged surrounding assertions.

The initial `/baam` summary and `baam.overview` query used this envelope.
