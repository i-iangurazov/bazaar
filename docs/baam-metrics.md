# BAAM metric contract

BAAM reuses the current **completed POS-sale reporting projection** through an [assistant interface](baam-assistant.md). Version `completed-sales-kgs-v1` is implemented by `getBaamSalesMetrics` in `src/server/services/baamMetrics.ts`. This metric service is deterministic and read-only; the assistant separately resolves supported requests locally or uses configured model interpretation. These contracts do not certify excluded POS/inventory producers or production source completeness.

## Scope and access

The caller supplies the authenticated server actor ID. The `baam.overview` router accepts only inclusive business dates and an optional store ID; the separate assistant input contract is documented in [BAAM business assistant](baam-assistant.md). Unknown input keys are rejected. The service rereads active membership, organization, ADMIN/MANAGER role, current subscription/analytics entitlement, and current organization-constrained store grants on every call. ADMIN and organization-owner managers can read their organization's stores. Other managers receive their granted stores only. A requested inaccessible store fails closed; an empty grant set never broadens to all stores. No platform-wide organization override exists.

Authorization and monetary reads share one PostgreSQL `REPEATABLE READ`, `READ ONLY` transaction. No response cache is used. Query identity hashes the metric version, organization, resolved ordered store IDs and exact UTC interval. The response audience identifies the authenticated actor; the client must not show another session's cached response. Revocations take effect on the next request; an already running transaction retains its start snapshot.

## Definitions

| Value | Exact meaning |
| --- | --- |
| Sales before returns | Sum of stored `CustomerOrder.totalKgs` for this organization/store scope, `isPosSale=true`, `isHeld=false`, `status=COMPLETED`, non-null `completedAt` in the period. This is already after recorded discounts. It is not undiscounted gross revenue. |
| Recorded discounts | Sum of those orders' `discountKgs`; informational, never subtracted a second time. |
| Returns | Sum of stored `SaleReturn.totalKgs` with `status=COMPLETED` and its own non-null completion time in the period. A return may relate to a sale outside the period. |
| Net sales | Sales before returns minus completed returns. Negative values are valid. This is not profit or tax revenue. |
| Receipt / return counts | Counts of the qualifying completed records, independently of payment-row count. |
| Average receipt | Sales before returns divided by receipt count, rounded to two decimals. BAAM returns `null` when there are no qualifying receipts. |
| Payment methods | Sum actual `SalePayment.amountKgs` rows grouped by CASH/CARD/TRANSFER/OTHER for the qualifying completed sales. Refunds are a separate breakdown. Both payment and related sale/return organization must match. Split rows sum; missing/overpaid rows are not fabricated or balanced. |
| Reconciliation | Payment sum minus sales, and refund sum minus returns. `paymentsReconcile` is true only when both differences round to zero. An empty scope can reconcile arithmetically without proving completeness. |

All monetary values are recorded KGS, rounded to two decimals after SQL aggregation. BAAM does not apply today's store exchange rate, infer historical FX or add currency balances together. The current report UI may format the same KGS values into the user's store display currency; that presentation conversion is outside BAAM's accounting contract. Current arithmetic uses JavaScript numbers after SQL decimals, as the existing reports do; large values beyond precise floating-point cent arithmetic are not certified.

Dates are valid `YYYY-MM-DD` calendar dates, ordered, at most 366 days. The configured business zone is `Asia/Bishkek` (UTC+06:00); the implementation uses that fixed offset. Date endpoints are inclusive in the business zone and translated to a half-open UTC range `[fromUtc, toUtcExclusive)`. September 1, 2026 starts at August 31 18:00 UTC. Future timezone-rule changes require a metric version and implementation review. Missing days are zero-filled. BAAM has no cashier/register inputs. Existing report cashier filters attribute a sale to its creator and a return to its completer, falling back to creator only if the completer is null; totals and refunds now use the same rule.

## Product and older chart boundaries

`getSoldProductsAnalytics` now unions sale and return activity **before** pagination and category/search filtering, so return-only products are included with zero sold quantity and negative net revenue/quantity. Product category options use both populations. Group identity is product ID plus variant key, and deterministic ordering is recorded sale revenue descending, sold quantity descending, name, product ID, variant key. Product metadata is current, organization-constrained metadata. Average price is sale line revenue divided by sold quantity, zero in the existing table if there were no sales. Separate order-wide adjustments are not allocated into product lines; summing product lines need not equal the order-level overview when the stored projections differ. Stock remaining is an existing supporting read, **not certified and not exposed by BAAM**; monetary tests stub that read and never access stock records.

The current sold-products export covers **all filtered results**, independently of the table page. `analytics.soldProductsExport` reads one authorized reporting snapshot with the selected dates, stores, register/cashier, category and search filters. It preserves product/variant identity, return-only rows, negative values and barcode strings. Current stock is absent. A result above 10,000 rows produces an explicit limit error; it is never silently truncated. Current role, organization, analytics and exports entitlements are checked before reading, with an authorization fingerprint checked again before returning the result.

CSV and XLSX downloads use the existing display-money formatter and shared spreadsheet encoding. The client discards a result when the authenticated audience or filters change, and checks again after asynchronous workbook generation before downloading. The earlier visible-page helper remains as a historical contract; the current report action uses `buildSoldProductsFilteredExport` and does not include a page number in its filename.

Older `analytics.getSalesTrend` / `getTopProducts` charts have a different contract: completed orders across channels, a rolling UTC period, no returns deducted, and existing 180-second cache. Historical line margin uses stored `lineCostTotalKgs`, otherwise stored `unitCostKgs × qty`; known zero cost is valid, any missing historical cost in the scoped population withholds the profit ranking, including missing cost below the top-ten cutoff. Current catalog prices/costs are never substituted. Rankings select the requested metric before LIMIT. These line margins exclude returns and separate order-wide adjustments and must not be described as business net profit. Their versioned cache separates organization, store set, range, bucket and ranking metric; equivalent sorted store sets may share a result. Cache corruption/outage behavior and simultaneous mixed-scope legacy arguments are not certified. BAAM bypasses this cache completely.

## BAAM catalog and product ranking

`executeBaamProductPlan` in `src/server/services/baamProducts.ts` reads a separate narrow projection. It does not call the existing sold-products function or read its supporting stock projection. The shared BAAM authorization check and product query run together in a `REPEATABLE READ`, `READ ONLY` transaction; the enclosing assistant also checks current grants before releasing its response.

The population is **current, nonarchived products with an active assignment to at least one selected accessible store**, scoped to the same organization. Archived, inactive-assignment, and unassigned products are excluded, including for administrators; this is deliberately a store-scoped catalog population. Products appear once even when assigned to multiple selected stores. Variants are combined at product level. Current assignments do not establish that a product was offered throughout a historical period.

Search matches literal name/SKU/barcode substrings using bound parameters; SQL wildcard characters in user text are escaped. Results expose canonical product-detail links, current category, first barcode, base unit, and current base price. Catalog evidence has `appliedPeriod=false`: those fields are not historical snapshots and dates do not filter them. A page/context product reference must match the current scoped population. A missing, archived, foreign, or inaccessible reference fails closed. Multiple matches produce a choice; a limit of one does not establish uniqueness.

Ranking and zero-sales evidence has `appliedPeriod=true`. Both use the same organization/store, completed/nonheld sale-channel and independent return-completion date rules above. **Net line revenue** is sale-line totals less return-line totals in KGS; separate order-wide adjustments are not allocated, so it need not equal overview net sales. **Net quantity** is sold quantity less returned quantity. Default ranking is net line revenue; an explicit quantity request ranks the numeric recorded base-unit quantity and warns that unlike base units are not directly comparable. Ties use product name then ID. Top/bottom ordering happens before the ten-result limit; the response states the total matching population and shown count.

The zero-sales tool selects zero qualifying **sold** quantity, not zero net quantity. Return-only products therefore remain visible with negative net figures. This is not a lifetime unsold claim, a stock check, an availability/demand estimate, or a recommendation to discontinue a product. Lifetime questions require a separate explicit scope decision rather than silently applying the selected short period. Product evidence states source, population, measurement, limits and query timestamp separately from the overview metric envelope. Query time does not certify upstream completeness.

The single-product `performance` action applies those same dated line-revenue, sold, returned and net-quantity definitions to one validated product page/conversation reference or a literal product lookup. It has `appliedPeriod=true`, unlike current catalog details. A missing reference asks for a product; multiple matches present choices without selecting one from a truncated list. Inaccessible references fail closed. The unique validated product reference can be retained for the next question. This action covers one selected period; it does not claim a product-level cross-period comparison or replace a product question with whole-store figures.

Focused tests run the actual SQL against connection-local TEMP catalog/sale/return projections with real persisted identities and grants in the disposable stabilization database. They cover aggregation across variants/assignments, returns, zero activity, business-date boundaries, channel/status/tenant/store exclusions, literal search, exact product references and revoked access. No operational producer, stock query, or live product/sale/return write is executed by those tests.

## Freshness and unknowns

BAAM report links use `/reports/analytics?dateFrom=YYYY-MM-DD&dateTo=YYYY-MM-DD&storeId=...`; omitting `storeId` explicitly selects all accessible stores. The shared `buildAnalyticsReportHref` helper validates real business dates and an inclusive range of at most 366 days. The report rejects partial, duplicate, unknown, and malformed query parameters. It waits for fresh authorized store choices and rejects an unavailable requested store without substituting all stores. No report query runs while scope validation fails, and stale figures are hidden during revalidation.

The URL is the source of truth for report dates and store. Manual date, preset, and store changes replace those parameters without scrolling; refresh and browser navigation restore the URL scope. A date/store URL or authenticated-audience change initializes the report atomically, resetting auxiliary filters, pagination, and open drilldowns so they cannot constrain a different store accidentally. Other filters remain local within that URL scope. The unparameterized report retains its existing last-30-days default.

`queryStartedAt` and `queriedAt` describe this database query, not when upstream business activity was fully ingested. `sourceCompleteness` is always `unknown`; `sourceCompleteThrough` is always null because no trustworthy watermark is available. A completed snapshot cannot prove no missing receipts, late returns, duplicates, offline uploads or upstream data errors. A zero means no qualifying value in that snapshot, not proof of no business activity. The metric response represents empty records, missing averages, payment differences and unknown completeness explicitly. The assistant renders the figures relevant to the question and includes its scope and evidence. It must never turn missing cost, unknown source coverage, absent data or a failed query into a confident financial explanation.

Excluded: profit, inventory/stock recommendations, demand forecasts, tax, expense/cash-flow accounting, all-channel revenue, customer/employee profiling, automated decisions, provider actions, and production-data reconciliation. No dedicated POS/inventory implementation or tests are part of this certification.

These tests certify implemented query semantics against controlled fixtures. They do not certify production source completeness, excluded producer correctness, high-volume performance or financial reconciliation against an external ledger. The earlier metrics-only audit did not inspect runtime model configuration; current live interpretation checks establish their recorded examples without inferring an unexposed model identity or general language accuracy.
