# Внутренний поиск по фото: реализованный прототип

14 ноября 2026 года. Ветка `codex/playground`. Изменения не развёрнуты в production.

## Пользовательский сценарий

В «Товарах» и на входе в кассу появилась кнопка «Поиск по фото». Пользователь выбирает
доступный магазин, делает снимок или загружает изображение. После подготовки фотографий
ассортимента PP-ShiTuV2 и Faiss находят до восьми похожих товаров. Показаны фотографии,
названия, артикулы при включённой настройке магазина, текущие цены и остатки этого
магазина. Пользователь явно выбирает подходящий результат.

В разделе товаров выбор открывает существующую карточку. В кассе результат выбирается
и просматривается внутри окна: продажа не создаётся, права на каталог не расширяются.
Это даёт доступ STAFF, который по действующим правилам не входит в раздел товаров.
Доступ одинаков на STARTER, BUSINESS и ENTERPRISE; нет оплаты за запрос и AI-кредитов.
Есть одинаковая защита от частых запросов и технический предел прототипа.

Фотография запроса не сохраняется. Товары без фото не участвуют. Не выдаются результаты
чужой организации, другого магазина, скрытые и архивные товары. Нулевой остаток допускается.
Результаты — кандидаты, а не автоматическое установление SKU. Подготовка карточек по фото
и внешние китайские площадки остаются следующими отдельными задачами.

## Реализация и отличия от целевой архитектуры

Используются [проверенная модель и параметры открытого стенда](product-photo-benchmark-20261114.md),
512-мерные нормализованные FP32 и готовый Faiss `IndexFlatIP`. Отдельного обучаемого
поискового движка нет. Python служба прогревает модель, проверяет файлы по SHA256,
принимает только защищённые внутренние запросы. Никаких HioBuy, TMAPI, OneBound или
DeepSeek в этом пути. Старый эксперимент 1688 удалён из списка интеграций и остаётся
выключенным по умолчанию; новый поиск не вызывает его и не использует его тарифный gate.

Прототип намеренно использует ограниченный вариант [целевой архитектуры](product-photo-workflows-architecture.md):

| Часть | Реализовано |
| --- | --- |
| Приём фото | Существующая клиентская подготовка, HEIC fallback, серверная проверка байтов, JPEG 1024 px, EXIF удалён, запрос до 3 МиБ |
| Данные | `ProductPhotoFeature`: составной FK с организацией, уникальность источника/версии модели, REAL[512], состояния подготовки |
| Синхронизация | Ленивая сверка при поиске, а не outbox в каждой транзакции товара. Изменённые фото исключены до подготовки свежих признаков |
| Обработка | Worker с атомарным захватом, арендой, тайм-аутом, тремя попытками, восстановлением и ручным повтором, чередованием организаций |
| Индекс | Перестраивается в памяти на каждый запрос только из текущих разрешённых признаков; общего каталога или кэша результатов нет |
| Ограничение объёма | До 10 000 активных товаров и 10 000 фотографий на магазин. Превышение — явная ошибка, не тихое усечение |
| Права | Те же проверенные сервером сессии и доступ к магазинам, повторная проверка после поиска; текущие сведения загружаются из БД |
| Тарифы | Тарифный gate отсутствует; проверены все роли и планы, в том числе отменённая подписка с сохранённым чтением |
| Защита от перегрузки | Redis: query 12/36 в минуту на пользователя/организацию; prepare 90/180; status 120/240. Один расчёт Python, занятость — 429 |
| Состояния UI | Подготовка, отмена, частичный поиск по согласию, пустая выдача, недоступная служба, ошибка и повтор, сброс при смене пользователя/организации/магазина |
| Языки | Русский, кыргызский, английский |

HTTP: `GET /api/products/photo-search?storeId=…`, `POST /api/products/photo-search/prepare`
и multipart `POST /api/products/photo-search`. Ключ внутренней службы хранится только
в окружении сервера/worker; `PRODUCT_PHOTO_SEARCH_URL` пуст по умолчанию. Подробные
[настройка, команды запуска и ограничения](../services/product-photo-search/README.md).

## Проверка

Одноразовые PostgreSQL 55991 / Redis 55992; отдельный пользователь `bazaar_test` и разрешённое
имя тестовой БД. Миграции применены с нуля. Подключения/секреты клиентов не использовались.
В тестах Node транспорт модели подменяется; отдельно проверены настоящий Faiss и полный
сценарий приложения с настоящей локальной моделью. Сторонние API не вызывались.

Проверены роли ADMIN/MANAGER/STAFF/CASHIER и все тарифы, подмена JWT-полей, отзыв доступа,
сессии и impersonation, составной FK организации, чужие магазины, скрытие товара во время
поиска, устаревшие фотографии, частичный набор, нулевая/отсутствующая цена, валюта магазина,
действующие/будущие/прошедшие скидки, остатки только выбранного магазина, повреждённые
и большие файлы, EXIF, ограничение запросов, ошибки модели, повтор и аренда worker.

Browser-сценарий `scripts/qa/product-photo-search-browser.mjs` создаёт четыре QA-товара
с открытыми ALOI-фото, галерея `r0/r90`, запрос — отдельное фото `103_r30`. Настоящие
PP-ShiTuV2 + Faiss нашли футбольный мяч. Проверены desktop 1440 и mobile 390, явное
открытие карточки у CASHIER на STARTER, пустой другой магазин на EN/KG, выбор без перехода
и без создания продажи у STAFF в кассе. Ошибок JavaScript и горизонтального переполнения
не обнаружено. Скриншоты и журнал создаются в `.local/product-photo-search/browser`.
Физическая камера телефона не проверялась: проверены файл, мобильная вёрстка и input capture.

## Перед рабочим включением

Это локально проверенный прототип. На целевом Linux-сервере нужно измерить установку,
CPU/RAM и параллельную нагрузку, а на разрешённых фото ассортимента — качество, похожие
варианты и порог. ALOI не подтверждает качество на клиентских SKU. Выбранный порог 0,68
может выдавать ложные похожие варианты, поэтому выбор всегда ручной.

Точный индекс на запрос упрощает изоляцию и обновление; верхняя граница передаёт около
27,3 МБ признаков между Node и Python и не является готовым решением для крупных сетей.
Для масштабирования предусмотрены версионированные индексы и outbox целевой архитектуры.
Расходы на собственный сервер остаются у Bazaar; платы пользователю за поиск нет.
Production, платные подписки и внешние площадки этим изменением не включались.

### Ручная проверка с телефона

При подготовке локального стенда для Wi-Fi найден существовавший сбой общего транспорта:
браузер на HTTP-адресе локальной сети не предоставляет `crypto.randomUUID`, и создание
служебного заголовка прерывало запросы ещё до отправки. Теперь оба транспорта tRPC
пропускают необязательный `x-request-id`, когда API недоступен; идентификатор создаёт
сервер через существующий `ensureRequestId`. Авторизация и ключи идемпотентности не меняются.
Добавлены три регрессионные проверки; вместе с проверками чтения POS и интерфейса поиска
прошли 14 тестов. Сборка и обычные проверки повторены.

Сам ручной стенд использует отдельный тестовый аккаунт и БД, dev-сервер на адресе
Wi-Fi Mac и обычный вход. Модель/worker/БД не открываются в локальную сеть. Временные
адреса, локальные учётные данные и фотографии ручного испытания хранятся только в
игнорируемом `.local/product-photo-search/manual`, не в исходниках и не в production.
