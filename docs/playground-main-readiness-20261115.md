Первый полный прогон фактически использовал установленный Node 24.7.0, вне закреплённого
диапазона проекта. Его нельзя называть полным зелёным прогоном на поддерживаемом Node.
Целевой повтор 108 тестов и production build выполнены явно на Node 22.23.4. Полный
финальный CI на закреплённом Node остаётся обязательным; один тест каталогового масштаба
по конфигурации запускается отдельно и не был включён в локальный полный прогон.

Причины первоначальных падений:

1. Consumption-аудит ожидал предыдущую ступень схемы, хотя актуальные миграции уже
   содержат upward rounding. Исправлены ожидаемая ступень и аргумент read-only проверки.
2. Сценарий Apple Production не задавал уже обязательные условия публикации и
   подтверждение новой редакции. Синтетическая конфигурация и helper согласованы с
   существующим контрактом; защитные проверки приложения не ослаблены.
3. Preview-signup обращался к жёстко заданному неработающему Redis `56361`.
   DB-интеграционный тест теперь использует явно переданный изолированный Redis.
4. Массовый minimum stock превысил 5 секунд во время параллельного инференса/нагрузки
   (5303 мс). При отдельном повторе прошёл внутри прежнего лимита, без изменения кода
   или ослабления теста. Это сохраняется как наблюдение о чувствительности к нагрузке,
   а не объявляется доказательством безусловной производительности на любом сервере.

## Условия дальнейшего выпуска

Перед разрешением на перенос всей ветки нужны обязательные проверки из текущего
release gate: security/dependencies, CodeQL, native Android/iOS, каталожный масштаб,
stabilization и соответствующие browser suites (inventory, BAAM, UX, reporting,
landing), контейнер WhatsApp worker. Их результаты не подменяются локальным Vitest.
Новый PR/запуск CI и слияние в main в этой работе не выполнялись. Если main изменится,
результат нужно снова сравнить с его актуальным состоянием.

Для активации фотопоиска отдельно нужны проверенная Linux-среда моделей, доступный
приватный Python-сервис и worker, проверка памяти/очереди/тайм-аутов на целевом сервере,
успешная подготовка фотографий и безопасная связь по серверному токену. Docker daemon
локально недоступен, поэтому Linux/контейнер не проверены. Нового платного посредника
или расходования AI-кредитов здесь нет. Технические ограничения одинаковы для всех
тарифов: в частности, максимум 10 000 изображений на область поиска.

Секреты `PRODUCT_PHOTO_SEARCH_URL` и `PRODUCT_PHOTO_SEARCH_TOKEN` остаются только на
сервере; пользовательский клиент их не получает. До настройки службы существующий
интерфейс честно показывает недоступность и повтор, без подставных результатов.
Схема `ProductPhotoFeature` и фоновый worker должны быть учтены при отдельном плане
миграции/запуска; текущее изменение UI новых миграций не добавляет. Самостоятельная
настройка сервиса, публикация или изменение production environment не выполнялись.

По качеству допустим только режим выбора из похожих товаров с понятными ограничениями:
на широком ассортименте есть существенные пропуски и путаница упаковок/сортов.
Автодобавление в продажу, изменение остатков и автоматическое создание карточки по
результату поиска не разрешены этим решением. Подробности и измерения — в
[отчёте широкого теста](product-photo-wide-20261115.md).

При откате будущего включения сначала убрать конфигурацию службы/остановить её
вызовы, затем вернуть код по плану релиза. Производные признаки можно перестроить;
не удалять исходные фото, товары и складские записи. Фактический rollback production
здесь не выполнялся и не проверялся. Рабочий ручной магазин оставлен доступным на
прежнем локальном адресе для дальнейшего тестирования.
