# PP-ShiTu и Chinese-CLIP: результаты сравнительного стенда

14 ноября 2026 года. Испытаны настоящие локальные модели на открытых фотографиях; платные API не использовались. Клиентские базы, фотографии Bazaar и production не затрагивались.

## Решение для Bazaar

**Для первого прототипа внутреннего поиска выбираем PP-ShiTuV2 с готовым кодировщиком PPLCNetV2 и точным поиском Faiss.** На этом стенде качество первой пятёрки совпало с Chinese-CLIP ViT-B/16, а PP-ShiTu быстрее, потребляет меньше CPU на запрос и имеет меньший пик памяти.

Это выбор технической основы прототипа по доступным открытым данным. Испытание на настоящих SKU/вариантах магазина и замеры на целевом Linux-сервере остаются условиями рабочего запуска. Полученные 99% нельзя переносить в обещание качества на ассортименте клиентов.

Chinese-CLIP сохраняем как проверенную альтернативу. Его возможности поиска по сочетанию изображения и китайского текста этим опытом не измерялись; подключать второй кодировщик в первый выпуск оснований нет.

## Основные результаты

Финальные замеры на Apple M4, CPU, 16 ГиБ RAM; GPU/MPS/CUDA не использовались. Числа относятся к прогретому локальному процессу с общим Faiss-исполнителем. p95 означает время, быстрее которого завершились 95% измеренных запросов.

| Показатель | PP-ShiTuV2 / PPLCNetV2 | Chinese-CLIP ViT-B/16 |
| --- | ---: | ---: |
| Правильный предмет на первом месте | 97,3% | 96,7% |
| Правильный предмет среди первых пяти | **99,0%** | **99,0%** |
| 95% интервал Recall@5, bootstrap по предметам | 98,3–99,6% | 98,4–99,6% |
| Один прогретый поиск, p50 | 36,6 мс | 57,3 мс |
| Один прогретый поиск, p95 | **37,3 мс** | **59,4 мс** |
| Четыре клиента, p95 с ожиданием очереди | **148,6 мс** | **232,5 мс** |
| Один клиент, измеренный локальный throughput | 27,2 запроса/с | 17,7 запроса/с |
| Среднее время CPU на один прогретый запрос | 36,7 мс | 65,9 мс |
| Средняя занятость CPU в фазе одиночного поиска, 100% = одно ядро | 100,2% | 116,0% |
| Память при прогретом поиске, суммарный RSS двух процессов | 883 МиБ | 962 МиБ |
| Максимальный измеренный RSS за весь прогон | 1 133 МиБ | 1 852 МиБ |
| Загрузка модели в новом процессе | 0,76 с | 3,40 с |
| Первый снимок после загрузки | 52,0 мс | 128,9 мс |
| Подготовка 600 фотографий галереи, batch 16 | 18,1 с | 26,2 с |
| Размер использованного официального пакета весов и файлов модели | 18,6 МиБ | 718,3 МиБ |

Разность Recall@5 PP-ShiTu минус Chinese-CLIP равна нулю; парный 95% bootstrap-интервал по 200 контрольным предметам — **от −0,7 до +0,7 процентного пункта**. Доказанного превосходства качества одной модели здесь нет. Выбор PP-ShiTu основан на ресурсах и задержке, а не на заявлении, что он точнее.

Размер Chinese-CLIP выше указан для полного официального checkpoint, включающего текстовую часть. При работе использовался только визуальный кодировщик, текстовый освобождался после загрузки. Отдельный экспорт только visual-весов мог бы уменьшить размер поставки и пик загрузки; такой экспорт не выполнялся и не выдаётся за измеренное преимущество PP-ShiTu. RSS включает фреймворки, обвязку, признаки и Faiss; маленький файл весов не означает такой же размер всей службы в памяти.

## Что именно сравнивали

- **PP-ShiTuV2**: официальный `general_PPLCNetV2_base_pretrained_v1.0_infer`, 512 признаков. Адаптер соответствует `inference_general.yaml` и `predict_rec.py` из [PaddleClas, commit 202ac79](https://github.com/PaddlePaddle/PaddleClas/tree/202ac79a99aa368f2c95cb1871bbc11574f685da). RGB, resize 224×224 bilinear, штатная нормализация, FP32 Paddle Inference. В Mac/ARM-профиле MKL-DNN выключен.
- **Chinese-CLIP ViT-B/16**: [официальный код, commit 31863c7](https://github.com/OFA-Sys/Chinese-CLIP/tree/31863c707501bf1605d36842f43deb78793dbc5d), [checkpoint OFA-Sys](https://huggingface.co/OFA-Sys/chinese-clip-vit-base-patch16), revision `36e679e65c2a2fead755ae21162091293ad37834`. Штатные bicubic resize и нормализация; FP32 PyTorch CPU; 512 признаков.
- Обе модели получают одни и те же исходные фотографии. Подготовка каждой соответствует её собственным опубликованным параметрам. Признаки нормализуются L2, далее одинаковый Faiss `IndexFlatIP` без приблизительного индекса и обучения. Несколько фотографий одного предмета объединяются до расчёта первых пяти результатов.

Это сравнение **кодировщиков и поиска для фотографии одного предмета**. Детектор основного товара PP-ShiTu, автоматическое выделение нескольких предметов на полке, текстовый поиск, OCR, DeepSeek и создание карточки не измерялись. Сравнение всех вариантов Chinese-CLIP и всех ускоренных/квантизованных экспортов также не проводилось.

Версии финального окружения: Python 3.13.7, PaddlePaddle 3.3.1, PyTorch 2.15.0, torchvision 0.29.2, Faiss CPU 1.16.0, NumPy 2.5.4. Полный [lock окружения](../scripts/benchmarks/product-photo/requirements-macos-arm64.lock.txt) сохранён отдельно от зависимостей приложения.

## Данные и контроль разделения

Использован [Amsterdam Library of Object Images, ALOI](https://aloi.science.uva.nl/aloi/description.html): фотографии реальных отдельных предметов при контролируемом изменении ракурса и освещения. Авторы: J. M. Geusebroek, G. J. Burghouts, A. W. M. Smeulders, *The Amsterdam Library of Object Images*, IJCV 61(1), 103–112, 2005.

С фиксированным seed `20261114` выбраны 400 идентичностей из 1 000: 300 присутствуют в каталоге, 100 отсутствуют. Использованы публичные JPEG-превью **154×115 пикселей**, а не полноразмерные оригиналы. Всего 2 400 файлов; синтетические запросы в оценку качества не включались.

| Часть | Данные |
| --- | --- |
| Галерея | 600 фотографий: по два ракурса `r0` и `r90` для 300 предметов |
| Подборочная выборка | 100 известных предметов × 5 условий + 40 отсутствующих × 3 условия: 620 запросов |
| Контрольная выборка | Другие 200 известных × 5 условий + другие 60 отсутствующих × 3 условия: 1 180 запросов |
| Условия известных запросов | `r30`, `r60`, `r180`, другое направление освещения `l3c1`, другая цветовая температура `i120` |
| Условия отсутствующих запросов | `r30`, `r180`, `i120` |

Каждый запрос — отдельная фотография, а не поворот/фильтр той же картинки. SHA256 всех файлов проверены; точных копий между галереей и запросами нет. Идентичности запросов подборочной и контрольной частей не пересекаются. Порог определяется только на подборочной части; контрольная не используется для его настройки.

Известные контрольные запросы дают следующие результаты:

| Условие | PP-ShiTu R@1 / R@5 | Chinese-CLIP R@1 / R@5 |
| --- | ---: | ---: |
| Ракурс 30° | 99,5% / 100% | 98,5% / 99,5% |
| Ракурс 60° | 97,5% / 99,5% | 95,5% / 99,0% |
| Обратный ракурс 180° | 90,0% / 95,5% | 89,5% / 96,5% |
| Другое направление света | 99,5% / 100% | 100% / 100% |
| Другая цветовая температура | 100% / 100% | 100% / 100% |

Основная трудность — обратная сторона предмета. Этот результат поддерживает включение нескольких настоящих ракурсов товара в индекс; он не обосновывает автоматическое назначение SKU по сходству.

## Товар отсутствует: существенное ограничение

Для каждой модели на 120 подборочных фотографиях отсутствующих предметов выбрали порог, допускающий максимум 5% ложных сигналов «найдено». Затем без изменения применили его к 180 контрольным фотографиям других отсутствующих предметов.

| Показатель контрольной части | PP-ShiTu | Chinese-CLIP |
| --- | ---: | ---: |
| Отсутствующий предмет получил высокий балл | **29/180 — 16,1%** | **21/180 — 11,7%** |
| Правильный первый результат известного предмета, прошедший порог | 91,1% | 88,9% |
| Неправильный первый результат известного предмета, прошедший порог | 1,0% | 1,1% |

Высокий Recall@5 не означает надёжное определение отсутствия товара. Простой порог не перенёсся с одной группы предметов на другую с желаемой частотой ошибок. Мы не подгоняли его по контрольной выборке, чтобы скрыть эту проблему.

Для Bazaar вывод конкретный: показывать кандидатов «Похожие товары», оставлять окончательный выбор человеку, не создавать остаток/продажу и не объединять карточки автоматически. Для различения близких вариантов использовать подтверждённые характеристики и штрихкод, когда он доступен. Уверенное «этот товар уже есть» и автоматический выбор по одному score этим стендом не подтверждены.

## Нагрузка и размер индекса

Модели запускались последовательно в отдельных процессах. Начальное `OMP_NUM_THREADS=1`; внутренние лимиты математики PyTorch/Paddle и Faiss — два потока на исполнитель. Это ограничение настроек, а не выделенные эксклюзивные ядра. Базовое время CPU включает кодировщик, обвязку и поисковый процесс.

При четырёх клиентах используется один исполнитель модели, поэтому увеличивается ожидание очереди, а не число копий модели. Это локальная имитация нагрузки, не измерение HTTP-сервера. Много организаций, одновременная индексация и поиск, R2, авторизация и PostgreSQL в испытании не участвовали.

Отдельно проверен общий Faiss на **синтетических** нормализованных векторах. Это замер стоимости индекса; качество на 50 тысячах разных товаров не заявляется.

| Векторов, по 512 float32 | Только матрица признаков | p95 Faiss в прогоне PP-ShiTu | p95 Faiss в прогоне Chinese-CLIP |
| --- | ---: | ---: | ---: |
| 1 000 | 2,0 МиБ | 0,032 мс | 0,034 мс |
| 10 000 | 19,5 МиБ | 0,326 мс | 0,333 мс |
| 50 000 | 97,7 МиБ | 1,745 мс | 1,612 мс |

Небольшое различие между колонками не характеризует качество моделей: движок и размеры векторов одинаковы. Для первого прототипа точный поиск выглядит достаточным; сложный приблизительный индекс пока не оправдан этими замерами. К матрице нужно прибавлять память фреймворков, копии при построении, идентификаторы и кэши магазинов.

Память измерялась каждые 20 мс как сумма RSS двух процессов. Общие страницы библиотек могут учитываться дважды, а очень короткий пик между отсчётами — не попасть в измерение. Поэтому это измеренный ресурсный профиль, не гарантия минимального лимита контейнера. Для размещения нужно учитывать пиковую загрузку модели и проверять профиль на целевом сервере, а не рассчитывать RAM по размеру файла весов.

## Совместимость и воспроизводимость

В доступных macOS-колёсах PyTorch и Faiss обнаружился конфликт копий OpenMP при использовании в одном процессе. Финальный стенд разделяет кодирование фото и Faiss через закрытую локальную пару сокетов. Опасный обход `KMP_DUPLICATE_LIB_OK` не используется. Время обмена включено в задержку; ресурсный учёт охватывает оба процесса.

Отдельный дефект первоначальной телеметрии при завершении временного дочернего процесса исправлен и покрыт тестами. После исправлений обе модели заново прошли один и тот же финальный код. Черновые результаты не включены в таблицы. Хеш исполняемой части стенда у обеих моделей совпадает:

## Границы вывода и следующий этап

Этот набор содержит реальные фотографии, но снят в лаборатории на чёрном фоне, имеет низкое разрешение и не размечен как ассортимент магазина с близкими фасовками/размерами. Пересечение публичных изображений с предобучением моделей полностью исключить нельзя. Задержки сняты на Mac с прогретыми файловыми кэшами и без эксклюзивного выделения CPU; Linux, обычная камера телефона и бизнес-операции не проверены.

Результатов достаточно, чтобы начать внутренний прототип **на PP-ShiTuV2 + Faiss** без платных поисковых API. До рабочего запуска нужны измерения на целевом CPU/Linux и отдельная проверка настоящих SKU, разных ракурсов и отсутствующих товаров выбранного магазина. Если она выявит недостаточное качество, повторно сравнить альтернативу на той же разрешённой выборке; не маскировать ошибки обещанием точного распознавания.

Визуальный поиск остаётся бесплатной функцией всех тарифов, с действующими правами и изоляцией магазина/организации. DeepSeek нужен только для отдельного сценария предложений полей нового товара и не участвует в текущем сравнении.

## Проверки этой поставки

Финальный запуск: `python scripts/benchmarks/product-photo/run.py --out .local/photo-search-benchmark/results-final` в изолированном venv. Экспорт отчёта проверяет совпадение manifest, хешей исходников и наборов контрольных запросов.

Пройдены восемь тестов протокола/телеметрии, компиляция Python-модулей, `pnpm typecheck`, `pnpm lint`, `pnpm i18n:check` и `git diff --check`. Экспорт доказательств также успешно проверил совпадение исходников, manifest и контрольных запросов. Production build не запускался: прикладной код, Prisma, клиентские экраны и Node-зависимости не меняются. База данных не использовалась.
